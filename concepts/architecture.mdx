Rubric is split into three pieces with crisp boundaries:

```
┌────────────────────────┐  bundle pull (every 30s)  ┌─────────────────┐
│  Your agent process    │ ─────────────────────────►│                 │
│  ┌──────────────────┐  │                           │  Control plane  │
│  │ Rubric SDK       │  │  audit events (batched)   │  (Fastify API)  │
│  │  - evaluator     │  │ ─────────────────────────►│                 │
│  │  - bundle cache  │  │                           │  ┌───────────┐  │
│  │  - audit sink    │  │  trace upload (per call)  │  │ Postgres  │  │
│  │  - trace upload  │  │ ─────────────────────────►│  └───────────┘  │
│  └──────────────────┘  │                           │                 │
│         ▲              │  JWT-SVID exchange/refresh│  Dashboard      │
│         │              │ ◄─────────────────────────│  (Next.js)      │
│         │ in-process   │                           │                 │
│  ┌──────┴──────┐       │                           └─────────────────┘
│  │  Tool call  │       │
│  └─────────────┘       │
└────────────────────────┘
```

## SDK — in your process

The SDK runs in-process, in the same Python interpreter as your agent. Three responsibilities:

- **Evaluator.** A pure-Python (or Rust, with `[runtime]`) interpreter for your policy bundle. `evaluate()` is sub-millisecond — no network round-trip on the hot path.
- **Bundle cache.** A background poller refreshes the bundle every 30 seconds. If the API is unreachable, the SDK keeps using the last-known-good bundle (fail-open by default; configurable).
- **Audit sink.** Every `evaluate()` enqueues an `AuditEvent`. A background flush thread batches them and POSTs to `/v1/events` (default: every second or 100 events, whichever first).

The SDK never blocks your tool dispatch on a network call. Outages of the control plane do not stop your agent.

## Control plane

The control plane is the API + dashboard your agents and operators talk to. What it does:

- Issues per-agent JWT-SVIDs (60-min lifetime, EdDSA-signed, auto-refreshed by the SDK)
- Stores policies (versioned, with diff and dry-run) and serves them as a signed bundle
- Ingests audit events and traces, emits incidents on deny spikes / DLP critical hits
- Hosts the dashboard for operators

The protocol surface (`/v1/...`) is small and stable. See the [REST API reference](/api-reference/introduction) for every endpoint.

## Trust model

Rubric is opinionated about *who can do what*:

| Actor | Credential | Can do | Cannot do |
| --- | --- | --- | --- |
| **Operator** | Clerk session (dashboard) | Manage policies, identities, enrollment tokens, see audit log | Forge an agent's identity |
| **Enrollment token** | `enr_...` (long-lived) | Call `POST /v1/identities/enroll` | Anything else (no audit ingest, no bundle reads) |
| **Agent (SDK)** | JWT-SVID (60-min) | Pull bundle, ship audit events for *its own* `agentId`, upload traces | Impersonate a different agent (server checks `sub` claim) |

The JWT's `sub` claim is the agent's stable id. Audit events and trace uploads are rejected if the `agentId` in the body doesn't match the token's `sub`. There is no other way to ship attribution.

## Failure modes

| Failure | What happens |
| --- | --- |
| Control plane down | SDK uses last-known-good bundle. Audit events queue in memory; flushed on recovery. |
| Bundle stale | `gov.current_bundle.bundleVersion` reflects the last successful pull. Optionally enforce a max-age in your harness. |
| JWT expired during outage | SDK auto-refreshes with `/v1/identities/refresh`. If the refresh endpoint is unreachable, the SDK retries and continues using the still-valid token until it expires. |
| Process restart with same `agentName` | Enrollment is idempotent — same `(orgId, agentName)` resolves to the same identity row. Fresh JWT, same `sub`. |
| Process restart with revoked identity | Enrollment returns `403 forbidden`. Operator must un-revoke or use a different name. |
